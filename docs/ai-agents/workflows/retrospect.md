# retrospect

Skip routine documentation-only save points unless a retrospective is asked
for explicitly. Inspect the session and relevant workflow, not unrelated
history. Identify concrete observations under Efficiency, Quality, Speed, and
Cleanup; distinguish demonstrated problems from preferences.

Turn useful findings into action. For each, state the evidence, consequence,
smallest useful change, and disposition: applied, proposed, or deferred.
Apply narrow corrections already covered by the user's authorization and
verify them. Do not stop at listing a problem when its fix is authorized.

For a change that needs a new decision or authorization, prepare a concrete,
reviewable proposal first, then present one focused question through the
interactive UI when available. Explain what needs agreement and why. Wait
before dependent work while continuing independent authorized fixes. Do not
ask again about choices or actions the user has already approved.

Promote agreed shared rules to canon. Capture substantive deferred work as
GitHub issues when publication is authorized; otherwise present the proposed
issue for agreement. A retrospective alone does not authorize external writes,
unrelated work, or a new commit/review cycle. Keep observations with no durable
value in the conversation. Reviewer findings stay in their own records.

Finish with changes made, checks performed, and any remaining concrete
proposal or next action. If no useful improvement is supported by evidence,
say so without manufacturing work. Do not optimize away real verification or
the deliberately sequential review stages.
